# Generated program lifetime — roadmap 3

The desktop/API NativeCompiler now loads each unique generated program into a collectible AssemblyLoadContext rather than a permanently retained Assembly.Load(byte[]) context. Its public Assembly-returning API, expression/function API, diagnostics, numerical code and unique identities are unchanged. Framework and application dependencies resolve through the default context, preserving shared type identity.

Ownership follows ordinary managed references: a chart or document retaining a Function/Delegate keeps that program alive. Once assemblies/types/delegates and executing frames are no longer rooted, the collectible context's runtime finalizer initiates unloading. The loader deliberately stores no generated assembly, subscribes to no global resolution event and introduces no cross-request compiled-function cache. It never unloads a function merely because an evaluator is reused for another expression.

`Program-Lifetime-Validate` and the normal core suite prove raw-compiler compatibility, reclamation of released scalar programs and generated exceptions, retained function behavior across collection, independent unsaved definition edits, repeated full expression compilation, dynamic delegate state and shared runtime-binder exception identity. NoInlining boundaries keep the test's JIT locals from artificially retaining the programs under test. Managed/private memory and assembly counts are recorded diagnostically; the scalar/exception gate is actual weak-reference reclamation, not an invented machine-specific memory ceiling. Run the full numerical/desktop/API suites as well before acceptance.

**Dynamic-program limitation:** the shared Microsoft.CSharp runtime binder retains generated context types in process-wide caches. On .NET 10.0.12, all 12 discarded dynamic programs in the review probe survived 20 full collection cycles, including after 5,000 distinct public binder calls exceeded its 4,096-entry binder-cache eviction threshold. The runtime's separate symbol/type caches mean that threshold is not a bound on retained programs or memory. The [10.0.13 binder](https://github.com/dotnet/runtime/blob/v10.0.13/src/libraries/Microsoft.CSharp/src/Microsoft/CSharp/RuntimeBinder/RuntimeBinder.cs) still interns context types through the same [type tables](https://github.com/dotnet/runtime/blob/v10.0.13/src/libraries/Microsoft.CSharp/src/Microsoft/CSharp/RuntimeBinder/Semantics/Types/TypeTable.cs). Generated dynamic operations, including portable matrix expressions, can therefore remain until process exit; collectible assembly status alone does not prove their reclamation. The regression suite records dynamic retention diagnostically while requiring unrelated scalar programs to collect. It does not clear private runtime caches, load an incompatible private binder, or claim prompt dynamic reclamation. Worker process exit provides the separate cleanup boundary for worker-backed web requests; desktop in-process dynamic lifetime remains follow-up work.

Collection is cooperative and not immediate deterministic disposal. User scripts that register global callbacks, start threads or keep native handles can retain their own state. This change does not terminate those threads or make full-trust execution safe; the separate execution-worker roadmap addresses cancellation/process lifetime. A chart must still release old Function references when removed; the tests establish the compiler/evaluator boundary, not every possible UI ownership path.

No forced collections are added to production, no package/solution changes, and no numerical tolerances are altered. See Microsoft's unloadability guide and .NET 10 AssemblyLoadContext source for the runtime's cooperative/finalizer behavior. Manual long-session acceptance remains useful in addition to these regression gates.
