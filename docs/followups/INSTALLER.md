# WixSharp / WiX installer migration

Cake is the orchestrator. `Installer-Source` publishes and launches a self-contained win-x64 .NET 10 product, builds the isolated WixSharp authoring tool, generates WiX source, and verifies nested payload inclusion, stable upgrade identity, file associations and product-version rules. The existing UpgradeCode **86D89770-B31B-4467-BC5E-B54B0FF263A1** and per-machine scope are preserved. ProductCode is deterministic per version/architecture: repair does not invent a new identity, a new version does. No old NetFx inference, XP branch or Framework runtime bootstrapper is used for the product.

The authoring host uses net481 because the selected WixSharp package is Framework-based. This is an isolated build tool, not a regression of the application to Framework. Old installer helper sources are retained for historical reference but are not compiled by the rewritten project. The authoring dependencies are explicitly pinned in this separate tool project; no per-project NuGet lockfile is introduced.

Current pins: **WixSharp_wix4 2.14.2**, **WiX 7.0.0**. WiX 7 requires explicit acceptance of its current licence/maintenance terms. The owner explicitly approved the local review build on 2026-10-13, and MSI/Burn compilation and MSI database validation succeeded. Source generation remains the default CI gate. `./build.ps1 -Target Build-Installer -CakeArguments '--accept-wix7-eula=true'` builds MSI and Burn bootstrapper with explicit opt-in; the workflow dispatch checkbox does the same. Review https://docs.firegiant.com/wix/osmf/ and https://www.nuget.org/packages/WixSharp_wix4 before opting in. No signing or release upload happens implicitly.

The MSI version comes from **Version.props**, currently the numeric identity for the **3.0.0-preview.1** review candidate. Edit that authoritative file and explicitly refresh the shared attributes as described in [release identity](../RELEASE-IDENTITY.md); an independent `--package-version` override must match it. Same-version upgrades are rejected, downgrade failures are visible, and the UI/associations match the historical product. The preview label is not encoded in MSI ProductVersion; these outputs remain candidates until release acceptance.

Source validation also checks that WixSharp discovers the repository's pinned local WiX tool. Keep the tool manifest in its multiline form: WixSharp 2.14's local-tool detection is line-oriented. After MSI compilation, the authoring tool opens the actual database read-only and checks product/upgrade identity, version, machine scope, x64 architecture, staged-file count, document associations and shortcuts. These checks do not install or register the application.

`Installer-Validate` can install, launch, repair and uninstall the produced MSI **only on an elevated disposable Windows machine** with `COMPUTATOR_DISPOSABLE_INSTALL_TEST=1`. It refuses to touch an existing Computator.NET installation and never invokes Win32_Product. It validates installed hashes and leaves external user-data files untouched. This is a real lifecycle test harness, not evidence that it has already run on a clean VM.

The manual GitHub workflow has a separate `validate_installer_lifecycle` checkbox, off by default. Together with explicit WiX acceptance it runs this harness against the just-built MSI, only on the disposable GitHub-hosted runner. This checks basic MSI installation, launch, repair and uninstall on an SDK-equipped machine. It does not certify a clean no-SDK environment, the Burn install/uninstall flow, historical upgrades, failed-upgrade rollback or signing. Lifecycle logs are retained even if cleanup fails.

Before release: rebuild the selected release version with approved tool terms; run the lifecycle harness on an OS with no SDK/shared .NET runtime; test upgrade from the actual historical 2.3.2 MSI and from the prior candidate; inspect both file associations and shortcuts; test rollback after failed upgrade; sign with an owner-controlled certificate in a protected release environment. The ordinary desktop installer must not expose the mathematical API as a service. Successful compilation and source/database validation do not certify installation or upgrades.

Self-contained output intentionally has neither trimming, NativeAOT nor single-file publication. Runtime servicing requires republishing the application. Stage changes must be reviewed with the separate GSL/MSIX workstreams; user profiles/documents must never be included in packaging globs.
