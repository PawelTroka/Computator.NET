# One product identity and release evidence — roadmap 4

Version.props is authoritative. `Release-Prepare` automatically expands the classic .NET `3.0.*` date/time convention once, freezes the timestamp and explicit values, and updates the compatibility attributes for review and commit before candidate CI. Assembly/file versions retain all four components; product/informational versions and release tags also carry the optional prerelease label. Ordinary builds validate the frozen identity without reading the clock or changing source. See [date/time preparation and platform projections](RELEASE-3.0.md#freeze-classic-net-datetime-versions).

MSI uses the first three components, while MSIX independently reserves its fourth component as zero. Mac short/build values are projected as `3.0.B` / `3.B.R`, retaining the time-derived revision within Apple's three-component build format. Native manifests record the full shared `productIdentity`. Preparation rejects conflicting published same-day MSI/MSIX identities and backwards clocks; an exact published retry preserves the original frozen timestamp and source files. No preparation target creates a tag, publishes assets, signs with an owner identity or submits to a Store. Publication status is recorded in [GitHub Releases](https://github.com/PawelTroka/Computator.NET/releases), rather than implied by a candidate's version alone.

Projects using checked-in shared assembly attributes retain a derived compatibility block. After deliberately editing Version.props, run `python build/release/versioning.py --write`, review both files, then build. Normal IDE/Cake builds compare the derived attributes and fail on drift; they never rewrite source. Portable SDK projects obtain the same version through Directory.Build.props. Independent MSI/MSIX argument overrides that would diverge from the product identity are rejected. The existing explicit AssemblyVersion declaration remains compatible with the ZIP builder.

`./build.ps1 -Target Release-Verify` validates the version mapping and negative self-tests, requires a clean tracked source revision, removes only known prior reports, and runs the existing Cake publication, focused browser, real browser/custom-function, portable, installer-source and unsigned-MSIX graphs. Child Cake invocations isolate their differing frontend deployment profiles. When the preceding local-web package module is present, its exact-package checks are included too. Native candidate and other OS matrices remain explicit additional release evidence rather than fabricated results from this Windows host.

The final manifest records the tested commit, timestamps, platform, actual test counts/report hashes, candidate file hashes and resolved NuGet package inventory. It requires the exact versioned ZIP/MSIX paths and fresh installer authoring; old or unrelated packages cannot fill missing outputs. The protected local package and both browser projects are required when that module is present. Missing/stale/incomplete/failed/duplicate reports are rejected; all required TRX and browser cases must pass without skips, including the implemented JSON 3D surface contract. NuGet inventory comes only from the supported projects restored by the developer-solution build; unchanged incremental restore files remain valid. The inventory is a release artifact, not a return of per-project NuGet lockfiles. Normal dependency pins/audits remain unchanged.

A candidate-evidence manifest is not a signed attestation or automatic release authorization. An operator with repository/workspace control can modify reports; protected CI and owner review still matter. Clean OS/historical-profile upgrade, visual acceptance, intended cross-platform jobs, actual signing and Store activation remain independent gates. No WiX EULA is newly accepted by this target; installer source verification does not claim an MSI lifecycle run.

When combining with the one-SLNX PR, link Version.props and these release helpers as developer solution items; no additional solution/project is needed. The 3.0 candidate identity deliberately changes the application's versioned native cache directory, not its user document/settings directory. Confirm Store version progression against the actual account before shipping; this repository cannot infer it.
